# Vinyl Backoffice — Strapi + Discogs

Backoffice slice for selling vinyl records on Discogs: a multi-tenant catalogue, one
sellable unit per physical copy, its listing on the channel, and a persistent log of every
marketplace operation.

Discogs runs in **mock mode by default** — the documented walkthrough needs no token and
makes no network call.

## Stack

- Strapi 5.52 (TypeScript)
- PostgreSQL 16 (Docker)
- Node.js 20
- Vitest

## Requirements

- Node.js 20
- Docker (for PostgreSQL)

## Install

```bash
cp .env.example .env          # then fill in the secrets, see below
docker compose up -d          # PostgreSQL 16
npm install
npm run develop               # http://localhost:1337/admin
```

On first launch, create the admin account through the interface. It is needed to browse the
data, but not to run the walkthrough below: the workflow endpoints are unauthenticated.

`.env` needs seven generated secrets. To fill them in one go:

```bash
cp .env.example .env
python3 - <<'PY'
import subprocess, re, pathlib
rnd = lambda: subprocess.check_output(['openssl','rand','-base64','32']).decode().strip()
p = pathlib.Path('.env'); t = p.read_text()
t = t.replace('APP_KEYS=', f'APP_KEYS={rnd()},{rnd()}', 1)
for k in ['API_TOKEN_SALT','ADMIN_JWT_SECRET','TRANSFER_TOKEN_SALT','JWT_SECRET','ENCRYPTION_KEY']:
    t = re.sub(rf'^{k}=$', f'{k}={rnd()}', t, count=1, flags=re.M)
pw = subprocess.check_output(['openssl','rand','-hex','24']).decode().strip()
t = re.sub(r'^DATABASE_PASSWORD=$', f'DATABASE_PASSWORD={pw}', t, count=1, flags=re.M)
p.write_text(t)
PY
```

Or fill them by hand: each is `openssl rand -base64 32`, and `APP_KEYS` takes at least two
comma-separated keys.

## Environment variables

| Variable | Role | Default |
|---|---|---|
| `HOST`, `PORT` | HTTP server | `0.0.0.0`, `1337` |
| `APP_KEYS` | session keys, ≥ 2 comma-separated | — (required) |
| `API_TOKEN_SALT`, `ADMIN_JWT_SECRET`, `TRANSFER_TOKEN_SALT`, `JWT_SECRET`, `ENCRYPTION_KEY` | Strapi secrets | — (required) |
| `DATABASE_CLIENT` | database driver | `postgres` |
| `DATABASE_HOST`, `DATABASE_PORT` | connection | `127.0.0.1`, `5432` |
| `DATABASE_NAME`, `DATABASE_USERNAME`, `DATABASE_PASSWORD` | credentials, also read by `docker-compose.yml` | — (required) |
| `DATABASE_SSL` | TLS | `false` |
| `DISCOGS_MODE` | `mock` or `api` | `mock` |
| `DISCOGS_API_TOKEN` | required only when `DISCOGS_MODE=api` | empty |
| `DISCOGS_API_BASE_URL` | Discogs API base | `https://api.discogs.com` |
| `DISCOGS_USER_AGENT` | User-Agent required by Discogs | `VinylBackoffice/0.1` |

`docker-compose.yml` reads the database variables from the same `.env` and fails with an
explicit message if they are missing, rather than starting with a default password.

`config/database.ts` is Strapi's generated file and was left untouched, so it also accepts
the standard optional variables — `DATABASE_URL` (connection string instead of the
individual fields), `DATABASE_SCHEMA`, `DATABASE_POOL_MIN` / `DATABASE_POOL_MAX`,
`DATABASE_CONNECTION_TIMEOUT` and the `DATABASE_SSL_*` family. They keep Strapi's defaults
and none of them is needed to run locally.

## Data model

```
Tenant ──< Product ──< SellableUnit ──1 ChannelListing
                                  │
MarketplaceSyncEvent >───────────┘   (also references Product and ChannelListing)
```

- **Product** — catalogue record: the release as a work. Carries `discogsReleaseId`.
- **SellableUnit** — one physical copy: its own SKU, price, grading and sale status.
  A product can have several.
- **ChannelListing** — publication state of a unit on a channel (`discogs` only here).
- **MarketplaceSyncEvent** — business journal, recording failures as well as successes.

Every business model carries a required `tenant` relation.

The **SKU** (`VIN-000001`) is generated by the backend from a PostgreSQL sequence; any
client-supplied value is discarded. Numbering has gaps by design — a sequence never
returns the same number twice, which matters more than being contiguous.

## Test walkthrough

With the server running, in another terminal:

```bash
npm run e2e
```

The script reseeds the demo data, runs the 10 steps below and asserts each response.
It is re-runnable: `--reset` deletes the demo tenant before recreating it.

```
0. Reseeding demo data
  ok   SKU was generated by the backend
1. Search a Discogs release
  ok   reference release 123456 is returned
  ...
All 19 checks passed.
```

### Running it by hand

```bash
npm run seed          # prints TENANT_ID, PRODUCT_ID, UNIT_ID and the generated SKU
export TENANT_ID=... PRODUCT_ID=... UNIT_ID=...
export API=http://127.0.0.1:1337/api
```

```bash
# 1. Search a release
curl "$API/discogs/search?tenantId=$TENANT_ID&q=Daft%20Punk"

# 2. Completeness before attaching — fails with RELEASE_NOT_ATTACHED
curl -X POST "$API/sellable-units/$UNIT_ID/check-discogs-completeness" \
  -H 'Content-Type: application/json' -d "{\"tenantId\":\"$TENANT_ID\"}"

# 3. Publishing while incomplete — refused with 400
curl -X POST "$API/sellable-units/$UNIT_ID/publish-discogs" \
  -H 'Content-Type: application/json' -d "{\"tenantId\":\"$TENANT_ID\"}"

# 4. Attach the release to the catalogue product
curl -X POST "$API/products/$PRODUCT_ID/attach-discogs-release" \
  -H 'Content-Type: application/json' \
  -d "{\"tenantId\":\"$TENANT_ID\",\"releaseId\":\"123456\"}"

# 5. Completeness after attaching — now valid
curl -X POST "$API/sellable-units/$UNIT_ID/check-discogs-completeness" \
  -H 'Content-Type: application/json' -d "{\"tenantId\":\"$TENANT_ID\"}"

# 6. Publish — returns discogs-listing-0001
curl -X POST "$API/sellable-units/$UNIT_ID/publish-discogs" \
  -H 'Content-Type: application/json' -d "{\"tenantId\":\"$TENANT_ID\"}"

# 7. Simulate a sale — unit becomes sold, listing becomes removed
curl -X POST "$API/sellable-units/$UNIT_ID/simulate-discogs-sale" \
  -H 'Content-Type: application/json' -d "{\"tenantId\":\"$TENANT_ID\"}"
```

The seeded unit deliberately has **no release attached**, so steps 2 and 3 demonstrate
refusal before steps 5 and 6 demonstrate success.

Data is visible in the admin under **Content Manager**. The journal is under
**Marketplace Sync Event**: after a full run it holds 7 events, two of which are failures.

## Endpoints

| Method | Path | Body / query |
|---|---|---|
| `GET` | `/api/discogs/search` | `?tenantId=&q=` |
| `POST` | `/api/products/:id/attach-discogs-release` | `{ tenantId, releaseId }` |
| `POST` | `/api/sellable-units/:id/check-discogs-completeness` | `{ tenantId }` |
| `POST` | `/api/sellable-units/:id/publish-discogs` | `{ tenantId }` |
| `POST` | `/api/sellable-units/:id/simulate-discogs-sale` | `{ tenantId, quantitySold? }` |

Status codes:

| Code | Meaning |
|---|---|
| `400` | invalid input, or unit not ready to be published (response carries `issues`) |
| `403` | tenant is inactive |
| `404` | resource unknown **or belonging to another tenant** |
| `502` | Discogs failed — an upstream outage, not a bug in this application |

A cross-tenant request returns `404` rather than `403`: answering `403` would confirm the
resource exists somewhere else.

## Discogs modes

**`DISCOGS_MODE=mock`** (default) — no network. Returns the Daft Punk fixtures, publishes
as `discogs-listing-0001` (incrementing). A query or seller comment containing
`FORCE_DISCOGS_ERROR` makes the connector fail, which is how the `sync_error` and `failed`
paths are exercised.

**`DISCOGS_MODE=api`** — requires `DISCOGS_API_TOKEN`. `searchReleases` and `getRelease`
call the real API. **`publishListing` throws**: creating a Marketplace listing requires
OAuth 1.0a, which a personal token does not provide. Failing loudly is deliberate —
returning a fake success would store the id of a listing that does not exist.

## Tests

```bash
npm test                 # 22 unit tests, ~200 ms, no database and no network
npm run test:integration # 6 tests, boots Strapi against the real database
```

Unit tests:

- `src/utils/sku.test.ts` — format, padding, overflow past 999999, invalid values
- `src/discogs/completeness.test.ts` — one case per business rule, error accumulation
- `src/discogs/mock-connector.test.ts` — search, unknown release, listing ids, failure path
- `src/discogs/index.test.ts` — mock/api selection, refusal of api mode without a token

They are deliberately kept offline, so `npm test` passes with the database stopped.

Integration test — `tests/integration/publish-discogs.test.ts` boots Strapi, listens on a
real socket and exercises `publish-discogs` end to end: refusal while incomplete, the
`failed` listing recorded, publication with its external identifiers, both journal entries,
and a cross-tenant request returning 404. It needs `docker compose up -d` and no server
already listening on the configured port.

`npm run e2e` additionally walks the full workflow against a running server.

## Design decisions and assumed limitations

- **Custom routes are unauthenticated** (`auth: false`). The specification asks for no
  authentication layer. In production `tenantId` would come from the token rather than the
  request body. This is a test-scope shortcut, not a production posture.
- **Tenant isolation is enforced in application code**, by filtering on `tenant` inside
  every query rather than by PostgreSQL row-level security. The filter sits in the query, so
  another tenant's row is never read in the first place.
- **`unique: true` is not a database constraint in Strapi 5** — it is validated in the
  application layer. A unique partial index on `sku` is therefore created at bootstrap, next
  to the sequence.
- **Publishing to the real Discogs Marketplace is not implemented** (OAuth 1.0a, see above).
- **No retry or queue** after a `sync_error`. The status makes a manual replay possible;
  a worker is out of scope.
- **Grading is optional at storage level** and required only to publish: a copy can enter
  stock before being graded. That is what makes the completeness check meaningful.
- **Tenants, products and units are created through the seed or the admin.** The generated
  REST routes keep Strapi's default permissions.
- `npm audit` reports vulnerabilities inherited from Strapi 5.52's dependency tree. No
  forced upgrade was applied, as it would change Strapi's own direct dependencies.
